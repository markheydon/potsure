## Clarifications

### Session 2026-11-09

- Q: Should a personal or household budgeter define a plan **start date** and **end date** for their budget? → A: No. The standing budget plan reflects what they know **as of today**: confirmed recurring bills and other outgoings, plus estimated income, until they change them. A bounded “budget period” on plan settings is not part of the household mental model for v1.
- Q: How do users see spending and income activity over time without plan dates? → A: Reports use a user-selected **report date range** (inclusive start and end calendar days) for period-scoped totals, category actual activity, commitments in scope for balance views, and related outputs. The report range is independent of pay dates and independent of how estimated income is expressed.
- Q: How should planned income be captured for a household user? → A: The user enters **estimated income** (amount they expect based on what they know today) and an **income cadence** (weekly, fortnightly, monthly, quarterly, or yearly). Weekly and monthly are the common cases. The system derives whatever normalised figures it needs for category allocations and forecasts from that pair; it does not ask for income totalled across a plan date window.
- Q: How do statement credits relate to income actuals? → A: Any imported **credit** that is not classified as an internal transfer or pot movement MAY be attributed by the user as income for actual receipt tracking (including one-off attribution and attribution via confirmed income patterns). Estimated income and actual attributed income MUST both be visible; actuals MUST include a rolling average of attributed income credits over a user-chosen window **capped at twelve months** maximum.
- Q: Do Session 2026-11-02 answers about a single working budget period and budgeted income for that period still apply? → A: **Superseded** for plan shape by this session. Inclusive date boundaries still apply to the **report date range**, not to a plan-period wrapper. Category allocations use **estimated income and cadence**, not a user-entered lump sum for an arbitrary plan window.
- Q: What does **three pots** mode allow? → A: **At most three** mapped bank pots in total, **at most one pot per** Needs, Wants, and Savings & Debt, with a strict **one-to-one** link between a mapped pot and its category (for example Needs → “My Needs Pot”). The system MUST enforce these limits while three pots mode is active. Mapping a pot to every category is **optional**; zero, one, two, or three category pots is valid.
- Q: What does **several pots** mode allow? → A: Any number of pots, each mapped to exactly one category, with **multiple pots allowed per category**. Mapping every category is still **optional**.
- Q: What happens when switching from several pots to three pots? → A: The mode change MUST be blocked until the user removes or remaps surplus pots so no category has more than one mapped pot and the total mapped pot count is at most three.
- Q: When should the system pre-select a pot during expense assignment (confirm recurring, one-off categorisation, merges/splits, transaction reassignment)? → A: In **three pots** mode, when the user selects a category that has a mapped pot, the system MUST pre-select that linked pot; if the category has no mapped pot, pot remains unset (none). In **several pots** mode, the user chooses among pots mapped to the category, except when **exactly one** pot maps to that category, in which case the system MUST pre-select that pot. In all cases the user MUST be able to change the pot to **none** or another valid pot for the category.
- Q: Can users change or remove confirmed recurring income and expense items after confirmation? → A: Yes. Users MUST be able to **edit** any confirmed recurring item they created (for example update a monthly rent amount after a rent-increase letter, change cadence, fixed vs variable behaviour, expense category, optional pot, tag, or income splits) and **delete** items that should no longer drive the plan. Edits MUST take effect for future matching, commitment projection, and forecasts from save onward. Delete MUST stop future matching and commitment use; stored transactions and existing attributions MUST remain unless the user changes them separately.
- Q: Can users maintain mapped bank pots when Monzo labels change or pots are removed? → A: Yes. Users MUST be able to **edit** a mapped pot (display name and category assignment within **FR-M013** mode rules) and **delete** mapped pots—including when trimming surplus mappings before switching to **three pots** mode. Deleting a mapped pot MUST clear optional pot references on confirmed recurring items to **none** and MUST NOT delete statement transactions.
- Q: When detection infers whether a recurring income or expense has a **fixed** or **variable** amount, can the user correct a wrong guess? → A: Yes. The system MAY infer fixed vs variable amount behaviour from statement history when suggesting patterns, but the user MUST be able to set or change that choice whenever they **confirm**, **merge**, **split**, or **edit** a recurring income or expense item (**FR-M008d**). A user override MUST be stored as authoritative for commitments (**FR-M018**), variable expense forecasts (**FR-M034**), runway warnings (**FR-M020**), and recurring summaries; the system MUST NOT silently revert an override on re-detection or re-import unless the user edits again.
- Q: When the report date range is not exactly one calendar month, how should category allocation on category health relate to actual activity in that range? → A: **Prorate** the **FR-M031** monthly category allocation amounts to the **inclusive report date range** (same time window as actual activity and expense commitments) so allocation, actual activity, and under/over always describe one range. Standing plan settings MAY show monthly-equivalent figures; report-scoped views MUST use prorated allocations. Proration MUST be deterministic (**FR-M036**); average month length **30.4375** days (see clarify session 2026-11-09).
- Q: For the budget balance yes/no (FR-M018), how should estimated income be expressed when expense commitments are projected into the selected report date range? → A: **Prorate** the standing plan’s **monthly-equivalent** estimated income to that **inclusive report date range** using the **same day-based proration rule** as category allocations (**FR-M017**). Yes/no, shortfall, and monetary gap MUST compare range-prorated estimated income to required income derived from range-projected expense commitments.
- Q: What should the default report date range be when the user opens a report and no in-session range is set yet? → A: **Current calendar month**: inclusive start = first calendar day of the month containing today, inclusive end = last calendar day of that same month. User may change the range; it is not persisted across sessions (**FR-X006**).
- Q: When the user budgets without any mapped bank pots, how should that relate to three pots and several pots modes? → A: **Three explicit choices:** **category-only** (no mapped pots; pot mapping limits and **FR-M013b** pre-selection do not apply), **three pots**, or **several pots**. Pot invariant rules apply only in the latter two. New users MAY default to category-only until they opt into bank-pot mapping.
- Q: In one browser session, should report views share one report date range or keep independent ranges? → A: **One shared report date range per browser tab** across all report views in that tab (category health, budget balance, runway, and related period-scoped outputs). Changing the range on any report in the tab updates the others in that tab; the range is not persisted across visits (**FR-X006**). *(Clarified 2026-11-09: not synchronized across separate browser tabs.)*
- Q: For a confirmed recurring expense marked **variable** amount behaviour, what monthly figure should **FR-M018** use when projecting expense commitments into the selected report date range? → A: A **user-confirmed monthly estimate** stored on the pattern (initial default from the system’s history-based suggestion at confirm, merge, split, or edit). That stored estimate feeds **FR-M018** commitment projection until the user saves an edit or **explicitly accepts** an updated suggestion; it MUST NOT change silently on import or report refresh. **FR-M034** computes rolling averages to inform suggestions and coverage labelling, not to auto-replace the stored estimate.
- Q: For runway warnings (**FR-M020**), over which dates should projected remaining spend be compared to prorated allocation minus actual activity plus recorded funding when both the report date range and forecast horizon apply? → A: **Runway window** = inclusive report range **start** through report range **end** plus **N** forecast-horizon months. **Category actual activity** counts only within the shared **report date range**; **expense commitment projection** and **prorated category allocation** for the comparison use the full runway window (same proration rule as **FR-M017**).
- Q: For day-based proration of monthly-equivalent allocations and estimated income (**FR-M017**, **FR-M018**), what average month length should v1 use everywhere? → A: **30.4375** calendar days (365.25 ÷ 12), applied uniformly: prorated amount = monthly-equivalent × (inclusive range day count ÷ 30.4375), rounded per report money rules (**FR-M036** golden scenarios MUST use the same divisor).
- Q: When the user enters estimated income with weekly, fortnightly, monthly, quarterly, or yearly cadence, how should v1 derive the **monthly equivalent** for category allocations (**FR-M031**)? → A: **Pay-period factors** on the entered amount: weekly × 52÷12, fortnightly × 26÷12, monthly × 1, quarterly ÷ 3, yearly ÷ 12; apply preset percentages to the result; round money at report or display boundaries only (**FR-M036**).
- Q: If the user has not yet chosen a length for the actual-income rolling average (**FR-M019**), what default should v1 use? → A: **3 months** (user may change up to twelve months); when attributed history is shorter than the chosen window, coverage MUST be labelled per **FR-M019**.
- Q: When projecting a confirmed **variable** expense’s stored monthly estimate into an inclusive report or runway range (**FR-M018**, **FR-M020**), should v1 use **30.4375** day-based proration (same as **FR-M017**) or calendar-month overlap apportionment? → A: **30.4375 day-based:** each variable pattern’s commitment in the range = stored monthly estimate × (inclusive range day count for that projection window ÷ **30.4375**), with money rounded at report boundaries per **FR-M036**; fixed patterns remain cadence-aware per-occurrence projection. Calendar-month overlap apportionment MUST NOT be used for variable commitments.
- Q: For the runway window end (**FR-M020**, **FR-M035**), how should v1 turn “report range end + **N** months” into a calendar end date before inclusive day-count proration? → A: **Calendar months from report end:** runway inclusive **end** = report range **end** plus **N** whole calendar months; when the resulting calendar day does not exist (for example 31 January plus one month), **clamp** to the **last calendar day** of that target month. Inclusive runway **start** = report range **start**. Day-count proration for allocation and variable commitments uses that inclusive start–end span (÷ **30.4375**).
- Q: Should the attributed actual-income rolling average window length (**FR-M019**) persist on the standing plan or reset each browser session? → A: **Persist on the standing budget plan** (default **3 months** when never set; user may change up to twelve months); export and return visits MUST reflect the stored value. The window length MUST NOT be in-session-only.
- Q: When a mapped pot with non-zero recorded funding is deleted (including before **category-only** mode), what should happen to that pot funding? → A: The user MUST **choose**: **roll** the pot’s recorded funding into the parent category’s recorded funding (once, no double count), or **discard** it. Deletion MUST require explicit confirmation when recorded funding is non-zero; discard MUST be stated clearly in that confirmation. Automatic discard without choice MUST NOT occur.
- Q: If the user opens multiple browser tabs to Potsure, should changing the report date range in one tab update the others? → A: **Per tab only.** Each browser tab keeps its own in-tab shared report date range; changing range in one tab MUST NOT update other tabs. Within a tab, all report views MUST still share one range (**FR-M031a**).
- Q: For a **fixed** confirmed recurring expense, which date should v1 use as the payment **anchor** when counting how many occurrences fall inside a report or runway range? → A: **Latest observed payment** from statement history: prefer the latest debit **attributed** to the pattern; otherwise the latest **vendor-matched** expense debit for that pattern’s grouping label. The user MAY **override** the stored payment anchor at confirm, merge, split, or edit (**FR-M008c**). Occurrence counts for **FR-M018** and **FR-M020** MUST use the stored anchor (user override or derived value); re-import MAY refresh a **non-overridden** anchor when a newer matching payment appears. When no matching payment exists yet, commitments from that pattern MUST be zero until the user sets an anchor or matching history appears.
- Q: For **FR-M018**, how should v1 combine per-category required incomes into the **overall** required income and pick the **limiting category**? → A: **Max-of-ratios:** for each category, required income = that category’s range expense commitments ÷ that category’s preset fraction (treat 0% as zero required). **Overall required income** = the **maximum** of the three per-category required incomes. **Limiting category** = the category with the highest per-category required income; ties MUST break in order **Needs**, then **Wants**, then **Savings & Debt**. **Shortfall** = max(0, overall required − range-prorated estimated income). **Yes/no balance** = range-prorated estimated income ≥ overall required income (**FR-M036** golden scenarios MUST match).
- Q: For the **actual-income rolling average** (**FR-M019**), which calendar span should attributed credits use? → A: **N whole calendar months** ending on the **report date range inclusive end** on period-scoped reports (category health, budget balance, runway, and related outputs sharing **FR-M031a**); ending on **today** on plan settings and other non-report plan views. Window **start** = first calendar day of the month that is **(N−1) months** before the month containing the end anchor (use last-day-of-month clamp when adding months to anchors, consistent with **FR-M020**). Include attributed credits whose transaction dates fall **inclusive** from that start through the end anchor. Displayed indication = total attributed credits in the window ÷ **N** as a **monthly mean** (distinct from **estimated income** and from expense actuals).
- Q: At report and golden-test boundaries (**FR-M036**, **SC-004**), how should v1 round GBP money to two decimal places? → A: **Banker's rounding** (round half to even) to **2 decimal places** at **each report emission boundary** (category health, budget balance, runway, plan report lines, and golden expected results). Intermediate calculation steps MAY use higher precision; emitted money values and golden fixtures MUST use the same rule.
- Q: When a user confirms a **fixed annual** (or other rare yearly) recurring expense, should **FR-M018** and **FR-M020** count **yearly occurrences** in the report or runway range? → A: **Yes.** Confirmed **annual/rare fixed** expense patterns MUST project into report and runway ranges using **amount per occurrence × yearly occurrence count** from the stored **payment anchor** (**FR-M008c**), with **annual** cadence stepping (same anchor rules as other fixed patterns). Detection (**FR-M007**) MAY miss some annual bills; when the user confirms or edits an annual/rare pattern manually, commitments MUST include it. Thin history MUST use explicit coverage labelling per **FR-M032** / **FR-M034** where relevant.
- Q: For a **fixed monthly** recurring expense, how should v1 count payment **occurrences** inside an inclusive report or runway range from the stored payment anchor? → A: **Step from the anchor** in whole **calendar months**, using **last-day-of-month clamp** when the anchor day is invalid in a target month (same rule as **FR-M020** runway month arithmetic). Generate all stepped occurrence dates forward and backward from the anchor; **count each date that falls inclusively inside the range**. Weekly and fortnightly fixed patterns continue to step by fixed day intervals from the anchor per **FR-M008c**; annual/rare fixed patterns use yearly stepping as already clarified. **FR-M036** golden scenarios MUST use this monthly rule.
- Q: When **FR-M034** computes the “last three months” average to **suggest** a variable expense’s monthly estimate, which calendar date should **end** that window? → A: **Today’s calendar date** whenever the suggestion is computed (confirm, merge, split, or edit on detection review or recurring summary). The window MUST be the **last three whole calendar months** inclusive through **today** (not the shared report date range end). Changing the report date range MUST NOT recompute or replace suggestions automatically. **FR-M018** / **FR-M020** commitments continue to use the **stored** monthly estimate, not a live rolling average.
- Q: After a user **rejects** a suggested recurring pattern and later imports statements with similar transactions, should v1 surface that pattern as a **new suggestion** again? → A: **Yes.** Later detection MUST be allowed to **suggest again** for the same merchant or grouping label; reject MUST NOT permanently suppress suggestions and MUST NOT auto-confirm on re-detection or re-import. Prior reject records MAY remain visible for audit but MUST NOT block re-suggestion.
- Q: Before the user has saved **estimated income** and **income cadence** on the standing plan, how should v1 treat **category allocations** and **budget balance** yes/no (**FR-M018**)? → A: **Incomplete / not set** until the user saves both amount and cadence: category allocation lines and **FR-M018** outputs MUST show an explicit unset state (not £0 planned income maths). Reports remain reachable; the system SHOULD prompt to complete plan income without blocking import or recurring confirmation. Income suggestions MUST NOT populate allocations until saved per **FR-M031**.
- Q: What **minimum and maximum** should v1 allow for the user’s **forecast horizon** **N** (months) that extend the runway window (**FR-M035**)? → A: **1–12 months** inclusive; default **3**; stored on the **standing budget plan** (same persistence as **FR-M019**). Values outside 1–12 MUST NOT be saved; the UI MUST guide the user back into range.

### Session 2026-11-04

- Q: What hosted authentication must v1 provide? → A: ASP.NET Core Identity with email/password register, sign-in, sign-out, and account isolation per user. Passwords are hashed by Identity; no plaintext storage. Hosted v1 MUST NOT require passkeys to sign in.
- Q: Where do passkeys fit? → A: Optional enhancement (same pattern as the .NET Blazor Identity template: password primary, passkey optional on login/register/manage when implemented). Passkeys are out of scope for v1.0.0 acceptance unless explicitly added in a later milestone; no “passkey-only hosted login” and no “no non-passkey login” rules.
- Q: Hosted reauthentication before export and permanent deletion? → A: User must reauthenticate using a hosted-appropriate challenge: prefer confirming the current account password (or the existing local-only typed phrase pattern adapted for hosted if password re-entry is unavailable in a flow). Passkey step-up MUST NOT be required for v1 acceptance.
- Q: Local-only mode? → A: Unchanged: account-free local-only mode, not network-exposed (**FR-M024**).
- **Planning note (UI, not a new FR here)**: Hosted account pages (register, sign-in, sign-out, manage) should behave like the .NET Blazor Identity template but be presented with BlazorBlueprint (**Bb***) components in Potsure.Web, not raw HTML/Tailwind from the stock template.

- Q: If an uploaded statement contains transactions in a currency other than GBP, what should v1 do by default? → A: Reject the upload (or non-GBP rows) with a clear error; no user override to import non-GBP amounts in v1.

- Q: When a user cannot use a passkey on their current device on a hosted instance, what should v1 offer? → A: *(Superseded by Session 2026-11-04  -  hosted v1 uses Identity email/password; passkeys optional and not required for acceptance.)* Former answer: passkey-only guidance with no non-passkey login.
- Q: For imported spending that does not match any confirmed recurring expense pattern - and is not manually categorised as a one-off - how should it affect category “actual activity” on category health? → A: Only debits matched to confirmed recurring or one-off categorisation count in category actuals; unmatched debits are excluded from categories but shown as uncategorised spend with a persistent visible warning until assigned.
- Q: When the same Monzo transaction appears twice within one file or across overlapping uploads, which rule should v1 use to treat two rows as the same transaction for de-duplication? → A: Prefer Monzo Transaction ID when available in the mapped CSV; otherwise duplicate = same date + amount + normalised description.
- Q: When an imported expense debit clearly matches a user’s confirmed recurring expense pattern, should v1 automatically count it toward that pattern’s category (and optional pot) in category actual activity without asking again on each import? → A: Auto-attribute matching debits to the confirmed pattern’s category and optional pot; user may reassign individual transactions; corrections persist on re-upload.
- Q: For a user-selected budget period with a start date and an end date, should imported transactions and period-scoped totals include activity on both the first and last day of that range? → A: *(Superseded 2026-11-09 for plan settings; still applies to the **report date range**.)* Both start and end dates inclusive (full calendar days) for report-scoped totals, actual activity, and commitment projection into that range.
- Q: If the user switches allocation preset (50/30/20 ↔ 75/15/10) while the same budget period is still selected, should category allocation amounts update straight away from the current budgeted income using the new preset? → A: *(Superseded 2026-11-09: no plan period.)* Immediate recalculation of category allocation amounts from the current **estimated income** (cadence-normalised) using the new preset; recorded funding, report-scoped actual activity, and standing commitments unchanged until the user edits them.
- Q: For the budget balance and required-income report (FR-M018), what should count as a period commitment when comparing planned income to the chosen preset? → A: *(Clarified 2026-11-09.)* Confirmed recurring expense patterns only, each projected into the selected **report date range** (cadence-aware); used with **estimated income** (cadence-normalised) and preset percentages for required income, limiting category, and yes/no balance.
- Q: Must genuine one-off transaction categorisation (**FR-M037**) ship in v1.0.0, or can that release rely on recurring match plus uncategorised-spend warnings until one-offs are added? → A: Required for v1.0.0  -  one-off categorisation is part of the first release (release gate for v1.0.0).
- Q: When a user adds an optional tag to a confirmed recurring expense (FR-M009), what should that tag represent in v1? → A: Optional free-text label for display and user reference in the recurring summary (and related lists); no effect on allocations, actuals, commitments, or budget balance calculations.
- Q: When a user defines allocation splits for a confirmed recurring income pattern across Needs, Wants, and Savings & Debt, what rule should v1 enforce on those split percentages? → A: Must sum to 100% across the three categories for each confirmed income pattern (validation blocks save otherwise).
- Q: In v1, should users be able to keep multiple saved budget periods (each with its own dates and budgeted income), or only one working period whose date range and income they change in place? → A: *(Superseded 2026-11-09.)* Former answer: single working period with dates and budgeted income. **Current:** one standing budget plan (estimated income, cadence, preset, confirmed recurring items); no library of saved plan profiles. Report date range is selected for views and is not a saved “budget period” entity.
- Q: For each category on category health, should under/over be computed as the category allocation minus actual activity only (recorded funding stays a separate line and does not change the under/over figure)? → A: Under/over = allocation − actual activity; recorded funding remains a separate measure and MUST NOT be subtracted in the under/over calculation.
- Q: When de-duplicating rows without a Monzo Transaction ID, how should the system normalise the description before comparing two rows (same date and amount)? → A: Trim; collapse internal whitespace to one space; strip non-alphanumeric characters; compare case-insensitively.
- Q: For category runway warnings (FR-M020), should recorded funding count toward covering projected remaining spend, so a warning appears only when projected remaining spend exceeds allocation minus actual activity plus recorded funding for that category? → A: Yes  -  warn when projected remaining category spend in the window exceeds (allocation − actual activity + recorded funding); optional mapped pot detail in the warning.
- Q: When a user merges two confirmed recurring expense patterns that disagree on category, pot, or tag, how should v1 resolve those assignments for the single merged pattern? → A: User must choose one category, optional pot, and optional tag for the merged pattern before save; future matches and stored attributions use the merged pattern and chosen assignments.
- Q: When a user splits one confirmed recurring expense pattern into two or more patterns, what must v1 require for category, pot, and tag before the split can be saved? → A: User must assign a category and optional pot/tag to each resulting pattern before save; save blocked until every split child is fully assigned.
- Q: For confirmed recurring income patterns with Needs/Wants/Savings & Debt splits totalling 100%, should those splits change any v1 calculations (category allocations, budget balance, or actual receipt breakdown), or stay display-only on the recurring summary? → A: Display-only  -  category allocations and FR-M018 use estimated income (cadence-normalised) and the chosen preset only; income splits appear on the recurring summary and related lists with no effect on allocations, commitments, expense actuals, attributed actual income, or budget balance.
- Q: When an imported refund or merchant credit is attributed to a budget category (via recurring match or one-off categorisation), should it reduce that category’s actual activity for the period? → A: Yes  -  category actual activity is net attributed spend: attributed expense debits minus attributed refunds/credits in that category (same attribution rules as debits).
- Q: How should v1 treat imported Monzo rows that are internal transfers (for example pot moves or paying yourself) rather than spending at a merchant? → A: Exclude from category actual activity and uncategorised spend by default when identifiable as non-spend transfers from statement data; user may one-off categorise to count as category spend if needed.
- Q: Should transactions classified as internal transfers or pot movements be excluded from recurring income and expense pattern detection? → A: Yes  -  exclude classified transfers from detection input entirely; they do not generate or feed suggested patterns.
- Q: When the user sets budgeted income for the working period, may v1 suggest a figure from confirmed income patterns projected into that period, as long as the user explicitly confirms or edits it before category allocations update? → A: *(Superseded 2026-11-09.)* **Current:** optional suggestion for **estimated income** (and compatible cadence where inferable) from confirmed income patterns or attributed credits; category allocations update only after the user confirms or edits estimated income (no auto-apply on import or pattern change).

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Import Monzo statements safely (Priority: P1)

As a lazy believer who avoids weekly spreadsheet upkeep, I upload one or more Monzo-format CSV files for my single Monzo account so my plan stays current from bank activity instead of manual entry.

**Why this priority**: Without trustworthy ingestion, no other budgeting value exists; silent loss or wrong-account imports would destroy trust immediately.

**Independent Test**: Upload valid, overlapping, and invalid files; verify de-duplication, explicit errors, account confirmation when identity is missing, and rejection of other banks or different accounts without importing their transactions.

**Acceptance Scenarios**:

1. **Given** a valid Monzo CSV for the user’s confirmed account, **When** the user uploads it and confirms or adjusts auto-detected column mapping, **Then** all parseable transactions are imported and a summary reports counts, date range, and any skipped rows with clear reasons, **And** rows identified as internal transfers or pot movements are excluded from category actual activity and uncategorised spend unless later one-off categorised as spend.
2. **Given** two uploads with overlapping transactions, **When** the second file is imported, **Then** duplicate transactions are not stored twice (matching by Monzo Transaction ID when present, else same date, amount, and normalised description per FR-M004) and the user sees how many were de-duplicated.
3. **Given** a CSV from another bank or a Monzo file that clearly belongs to a different account, **When** the user attempts import, **Then** the import is rejected and no transactions from that file are stored.
4. **Given** a Monzo CSV with no reliable account identity, **When** the user starts import, **Then** the system requires explicit user confirmation of account identity before persisting transactions.
5. **Given** a malformed or unsupported file, **When** import runs, **Then** the user receives clear errors and no transactions are silently dropped without explanation.

### User Story 2 - Detect and confirm recurring patterns (Priority: P1)

As a user with irregular pay and multiple income sources, I want the app to suggest recurring income and expenses (weekly, fortnightly, monthly) so I can confirm, merge, split, reject, or later **edit or delete** each confirmed item when my situation changes, without assuming a fixed payday.

**Why this priority**: Recurring detection drives estimated income suggestions and expense commitments; user confirmation and income attribution keep forecasts honest when history is short.

**Independent Test**: Import one to three months of data; review suggested patterns; confirm, merge, split, reject, edit, and delete; verify income patterns define sources and splits while expense patterns receive category (and optional pot/tag) assignment; override inferred fixed vs variable when wrong and verify commitments and forecasts follow the stored choice (**FR-M008d**); verify an edited monthly expense amount updates commitments.

**Acceptance Scenarios**:

1. **Given** at least one month of statement history, **When** detection runs, **Then** the user sees suggested recurring income and expenses separately from confirmed items, with cadence and a suggested fixed or variable amount indication where inferable (**FR-M008d**), **And** rows classified as internal transfers or pot movements are not included in detection input.
2. **Given** variable or ad-hoc income, **When** the user reviews income, **Then** they can confirm amounts without forcing a recurrence pattern or fixed payday.
3. **Given** a user confirms a detected expense pattern, **When** they assign Needs, Wants, or Savings & Debt and optionally a mapped bank pot and tag, **Then** that assignment is stored and appears in the confirmed recurring summary, **And** optional pot pre-selection follows **FR-M013b** when category is chosen or changed.
4. **Given** a user confirms an income pattern, **When** they define allocation splits across budget categories, **Then** expense category assignment is not applied to income patterns, **And** the three split percentages MUST sum to 100% before the pattern can be saved, **And** those splits MUST NOT alter category allocation amounts, FR-M018 results, or actual receipt breakdown (display-only on recurring summary and related lists).
5. **Given** two confirmed expense patterns with differing category, pot, or tag, **When** the user merges them, **Then** they MUST choose one category, optional pot, and optional tag for the merged pattern before save, **And** subsequent matching and stored attributions apply to the merged pattern with those assignments.

### Edge Cases

- Income pattern split percentages that do not total 100% MUST be rejected on save with a clear validation message.
- Budget balance and required income (FR-M018) use expense commitments from confirmed recurring **expense** patterns only (cadence-projected into the selected **report date range**); income patterns, one-offs, recorded funding, and unattributed imports are excluded from commitment totals.
- Upload contains duplicate rows within the same file versus duplicates across files; both must de-duplicate with reported counts using Monzo Transaction ID when mapped and present, otherwise same date, amount, and normalised description (trim, collapse internal whitespace, strip non-alphanumeric characters, case-insensitive compare).
- Upload spans gaps in calendar coverage; reports and forecasts disclose missing history.
- Only one month of history on first use; detection may be incomplete - user-led confirmation remains available without blocking onboarding.
- Annual or rare payments with multi-year history; detection may miss some - limits are disclosed, not guaranteed complete. User-confirmed **annual/rare fixed** patterns MUST still project yearly occurrences into **FR-M018** and **FR-M020** from the payment anchor.
- Variable recurring amounts with fewer than three months of history; **FR-M034** suggestions use available calendar months with explicit coverage labelling; window ends on **today** when computed, not on report range end.
- Income arrives on irregular dates (self-employed, multiple sources); standing plan and report date range do not require aligning to a payday.
- User maps multiple expense pots to the same category in **several pots** mode; totals still aggregate once at category level; three pots mode MUST NOT allow more than one pot per category.
- User switches pot mapping mode from several pots to three pots while surplus mappings exist; mode change remains blocked with guidance until at most one pot per category and at most three pots total.
- User switches from three or several pots to **category-only** while mapped pots remain; switch blocked until all pots deleted per **FR-M013c**; optional pot references on recurring items clear when pots are removed.
- **Category-only** mode: no pot mapping UI, no **FR-M013b** pre-selection, no pot-count limits; full category-level budgeting and recorded funding at category level remain available.
- User assigns expense category in three pots mode with no pot mapped to that category; pot assignment remains none until the user optionally maps a pot or selects none explicitly.
- User changes expense category after a pot was pre-selected; pre-selection MUST update to the new category’s linked pot under three pots mode, or to the single-pot rule under several pots mode, or clear when no default applies; user MAY still set pot to none.
- User attempts to exceed category allocation across pots plus unassigned amounts; system saves the entries and shows a persistent visible over-allocation warning on category health until corrected.
- Account identity ambiguous across sequential uploads; user must confirm before merge.
- Re-import after partial deletion or export; behaviour remains consistent with de-duplication and remembered assignments.
- Same stored inputs and settings viewed twice; category health and budget balance totals match on both views.
- Report date range boundaries are inclusive of both start and end calendar dates for transaction inclusion and report-scoped totals.
- Report date range spans more or fewer than one calendar month: category **allocation** on category health and in **FR-M020** runway maths MUST use monthly-equivalent allocations from **FR-M031** **prorated** to that inclusive range (not unprorated monthly figures compared to multi-month actuals).
- Day-based proration for allocations and range-scoped estimated income: inclusive calendar-day count ÷ **30.4375** × monthly-equivalent; same divisor on category health, budget balance, runway, and golden scenarios (**FR-M036**).
- **FR-M018** budget balance for a non-month-long report range: estimated income side of yes/no and shortfall MUST use monthly-equivalent estimated income **prorated** to that range (**same rule** as **FR-M017** allocations), not unprorated monthly income compared to range-total commitments.
- v1 exposes one standing budget plan (estimated income, cadence, preset, recurring confirmations); no library of saved plan profiles or saved report-range presets beyond the current selection in session.
- First report open in a session with no range yet: default report date range MUST be the **current calendar month** (inclusive first through last day of the month containing today) per **FR-M031a**.
- One **shared report date range per browser tab**: changing the range on category health MUST apply the same inclusive range to budget balance, runway, and other period-scoped views in **that tab** (**FR-M031a**); other tabs MUST NOT auto-sync.
- User changes allocation preset on the standing plan; category allocations recalculate immediately from estimated income (cadence-normalised); recorded funding, report-scoped actual activity, and standing commitments remain until user updates them (may trigger over- or under-allocation warnings); under/over recalculates from updated allocation minus unchanged actual activity.
- Forecast horizon shorter than recurring cadence (e.g. weekly bill, one-week horizon); warnings remain mathematically consistent and labelled.
- Forecast horizon **N** outside **1–12 months**: save MUST be rejected or clamped with clear validation; default **3** when never set (**FR-M035**).
- Category runway warning uses runway window report start through **runway end** (report end + **N** calendar months, last-day clamp); projected commitments across that window compared to runway-prorated allocation minus **report-range-only** actual activity plus recorded funding (pot funding rolled up at category level); optional pot detail in messaging.
- Permanent deletion is irreversible; export is offered as the recovery path before deletion.
- Hosted sign-in or registration problems (unknown account, wrong password, unconfirmed email where enforced, lockout): user MUST receive clear Identity-appropriate messaging and paths to register, sign in, or reset password where implemented; passkey step-up MUST NOT be required for v1 acceptance.
- Currency other than GBP in a file; import MUST reject the upload or affected rows with a clear error and MUST NOT offer an override to persist non-GBP amounts in v1 (no silent conversion).
- Confirmed recurring income pattern splits totalling 100% are display-only; category allocations and budget balance use estimated income (cadence-normalised) and preset only, not per-pattern splits.
- Confirmed recurring **rejected** then similar transactions appear: detection MUST offer the pattern as a **new suggestion** again; reject MUST NOT permanently suppress that grouping; the system MUST NOT auto-confirm on re-import or re-detection.
- User merges confirmed expense patterns with conflicting assignments; system requires choosing one category, optional pot, and optional tag before save; merged pattern drives future matches and attributions.
- User splits a confirmed expense pattern; each resulting pattern must have category (and optional pot/tag) assigned before save is allowed.
- Imported expense debits unmatched to confirmed recurring and not one-off categorised must not count toward category actual activity; uncategorised spend total and persistent warning remain until user assigns each debit.
- Attributed refunds or merchant credits reduce category actual activity (net attributed spend); unattributed refunds or credits do not change category actuals until assigned with the same rules as debits.
- Rows identifiable as internal transfers or pot movements (non-merchant spend) are excluded from category actual activity and uncategorised spend by default; import summary reports how many were classified as transfers; user may one-off categorise a transfer as category spend when appropriate.
- Classified internal transfers and pot movements are excluded from recurring pattern detection input and MUST NOT produce suggested recurring items.
- Estimated income and cadence may be suggested from confirmed income patterns or attributed credits; allocations MUST NOT change from a suggestion until the user confirms or edits estimated income.
- Standing plan with **no saved estimated income and cadence**: category allocations and **FR-M018** MUST show explicit **not set** state (not zero-income maths); reports stay reachable; import and recurring flows MUST NOT be blocked.
- Estimated income cadence to monthly equivalent: weekly × 52÷12, fortnightly × 26÷12, monthly × 1, quarterly ÷ 3, yearly ÷ 12, before preset application (**FR-M031**).
- Credits not classified as internal transfers MAY be attributed as income; unattributed credits do not affect attributed actual income totals or the rolling actual-income average until attributed.
- Rolling actual-income average MUST use only user-attributed income credits; window length **N** persisted on standing plan, default **3 months** when unset (**FR-M019**); user-chosen **N** MUST NOT exceed twelve months; window ends on report range **inclusive end** on reports or **today** on plan settings; shorter history MUST use available attributed credits with explicit coverage labelling when below the chosen window.
- User edits confirmed recurring expense amount (for example rent increase); budget balance and runway projections MUST use the new amount from save onward; historical category actual activity from past imports is unchanged unless transactions are reassigned.
- User deletes a confirmed recurring item that previously drove auto-attribution; re-import MUST NOT re-apply that deleted pattern automatically; similar transactions MAY appear as new suggestions.
- User deletes a mapped pot still referenced by confirmed recurring items; those items MUST show no pot after deletion; category assignments and tags remain.
- User deletes a mapped pot with recorded funding while switching to **category-only** or trimming mappings; system MUST offer roll-up to parent category funding or discard with explicit confirmation when funding is non-zero (**FR-M013c**).
- User attempts pot category reassignment that would break three pots mode limits; save MUST be blocked with a clear message until valid under **FR-M013**.
- Detection suggests variable amount behaviour for a bill the user treats as fixed (or the reverse); user MUST be able to override at confirm or edit; **FR-M018** and **FR-M034** MUST follow the user’s stored choice, not the latest inference alone.
- User merges or splits patterns that disagreed on fixed vs variable behaviour; user MUST choose or assign fixed vs variable per resulting pattern before save; chosen behaviour MUST persist per **FR-M008d**.
- Confirmed recurring **variable** expense: **FR-M018** and **FR-M020** use the stored user-confirmed **monthly estimate** prorated with the **30.4375** day-based rule (same as **FR-M017**), not calendar-month overlap; **FR-M034** rolling average MAY be offered as an explicit suggestion only, never applied without user save or acceptance.
- Confirmed recurring **fixed** expense before any matching payment in history: **FR-M018** / **FR-M020** occurrence count is zero until the user sets a payment anchor or a matching debit appears; user override MUST NOT be replaced silently when newer payments import unless the user clears override.
- **Fixed monthly** expense occurrence counting: step from the payment anchor in whole calendar months with last-day-of-month clamp when needed; count stepped dates that fall inclusively inside the report or runway range (**FR-M018**, **FR-M020**, **FR-M036**); do not use per-calendar-month slots without walking from the anchor.
- Two categories tie for highest required income on budget balance: limiting category MUST resolve **Needs**, then **Wants**, then **Savings & Debt** (**FR-M018**).
- Report money display and golden scenarios: half-pence ties MUST use **banker's rounding** to 2dp at emission (**FR-M036**), not inconsistent per-page rules.

### Functional Requirements  -  Must

- **FR-M001**: The system MUST accept upload of one or more Monzo-format CSV statement files per user for a single Monzo account only.
- **FR-M002**: The system MUST auto-detect Monzo CSV column mapping when the layout matches a known Monzo export; the user MUST confirm or adjust mapping before import proceeds; unchanged layouts MUST reuse the remembered mapping. The system MUST reject unsupported formats with clear errors.
- **FR-M003**: The system MUST NOT silently drop transactions; every skipped or failed row MUST be reported with a reason. Rows classified as internal transfers or pot movements MUST be reported in the import summary (counts and reasons) and MUST NOT contribute to uncategorised spend or category actual activity unless the user later one-off categorises them as spend.
- **FR-M004**: The system MUST de-duplicate imported transactions within a file and across overlapping uploads and report de-duplication counts. Two rows represent the same transaction when they share the same Monzo Transaction ID from the mapped CSV, or - when that ID is absent for either row - when they share the same transaction date, amount, and **normalised description**. Normalisation for comparison MUST: trim leading and trailing whitespace; collapse runs of internal whitespace to a single space; remove all non-alphanumeric characters from the description; compare the result case-insensitively.
- **FR-M005**: The system MUST reject other banks’ CSV layouts and files identifiable as a different account without importing their transactions.
- **FR-M006**: When account identity is absent or ambiguous, the system MUST require explicit user confirmation before persisting transactions.
- **FR-M007**: The system MUST detect recurring income and expenses with cadences including weekly, fortnightly, and monthly where evidence exists; annual or rare cadences MAY be suggested when evidence exists but completeness MUST NOT be guaranteed (**FR-M032**). The user MUST be able to confirm, merge, split, or edit patterns with **annual/rare** cadence manually; such confirmed **fixed** patterns MUST feed commitment projection per **FR-M018** / **FR-M020**. Transactions classified as internal transfers or pot movements (per **FR-M003** / import classification rules) MUST be excluded from detection input and MUST NOT generate suggested recurring patterns.
- **FR-M008**: The system MUST allow confirmation, merge, split, and reject for each detected pattern and MUST separate confirmed from unconfirmed suggestions. **Reject** MUST record the user’s decision without confirming the pattern; it MUST NOT auto-confirm that pattern on later imports or detection runs. Reject MUST NOT permanently suppress future suggestions for the same merchant or grouping label  -  later detection MUST be permitted to surface a **new suggestion** again, which the user may confirm, reject again, or ignore. When the user merges two **confirmed recurring expense** patterns whose category, optional pot, or optional tag differ, the system MUST require the user to choose a single category, optional pot, and optional tag for the merged pattern before persisting; subsequent auto-attribution and assignment memory MUST use the merged pattern and those chosen assignments. When the user splits a **confirmed recurring expense** pattern into two or more patterns, the system MUST require a category assignment (and optional pot and tag) for **each** resulting pattern before persisting the split and MUST block save until every resulting pattern has a category assigned.
- **FR-M008c**: The system MUST allow the user to **edit** and **delete** any **confirmed recurring** income or expense item created through the detection and confirmation workflow. **Edit** MUST support at least: display label or merchant grouping identity where shown; cadence; fixed or variable amount behaviour (including override per **FR-M008d**); for **fixed** expenses  -  expected amount per occurrence, cadence (including **annual/rare**), and optional **payment anchor date** used for cadence-based occurrence counting (default: latest attributed payment, else latest vendor-matched debit; user override persisted until cleared); for **variable** expenses  -  **monthly estimate** used for **FR-M018** commitment projection and **FR-M020** runway maths (initial default from history-based suggestion per **FR-M034**, always user-editable); for income  -  allocation splits per **FR-M010**. Edited values MUST apply to future matching, **FR-M018** expense commitment projection, variable expense estimates (**FR-M034** / stored monthly estimate), and income attribution rules from the time of save. The stored **monthly estimate** for variable expenses MUST NOT update from imports or detection alone; the user MUST save an edit or explicitly accept a refreshed suggestion. **Delete** MUST require user confirmation, remove the item from the confirmed recurring set, and stop future matching and commitment use for that item; it MUST NOT delete stored statement transactions. Per-transaction attributions and assignment memory (**FR-M010a**, **FR-M010b**) MUST remain as stored until the user changes them. A deleted item MAY be suggested again on later detection if matching transactions appear.
- **FR-M008d**: For each recurring **income** or **expense** pattern, the system MAY infer whether amounts are **fixed** or **variable** from statement history when presenting suggestions. The user MUST be able to set or change fixed vs variable amount behaviour whenever they **confirm**, **merge**, **split**, or **edit** that pattern; inference MUST NOT lock the choice or prevent save. The user’s stored choice MUST be authoritative for **FR-M018** commitment projection (fixed vs variable treatment), **FR-M034** variable expense forecasts, **FR-M020** runway projections, and **FR-M021** summaries. Re-running detection or importing additional statements MUST NOT change a confirmed pattern’s fixed vs variable behaviour unless the user edits it again. When the user merges or splits expense patterns, each persisted resulting pattern MUST have an explicit user-visible fixed vs variable assignment before save (defaulting to the system suggestion when shown, always changeable).
- **FR-M009**: The system MUST assign confirmed expense patterns to exactly one of Needs, Wants, or Savings & Debt, with optional mapped bank pot and optional **tag** (free-text label for display only; MUST NOT affect allocations, actual activity, commitments, or budget balance maths).
- **FR-M010**: The system MUST treat income patterns as sources with allocation splits across Needs, Wants, and Savings & Debt, not as expense category assignments. For each confirmed income pattern, split percentages MUST sum to exactly 100%; the system MUST reject save until satisfied. Income splits MUST be **display-only** labels on the recurring summary and related lists; they MUST NOT affect category allocations (FR-M011), expense commitment projection, category actual activity, attributed actual income, or budget balance calculations (FR-M018).
- **FR-M010a**: The system MUST remember expense assignments and user corrections on re-upload. Expense debits that match a confirmed recurring expense pattern MUST be auto-attributed to that pattern’s category and optional pot for category actual activity without per-import re-confirmation; attributed refunds or merchant credits MUST reduce category actual activity under the same assignment rules. The user MUST be able to reassign individual transactions, and those corrections MUST persist on subsequent imports.
- **FR-M010b**: The system MUST allow users to attribute imported **credits** as income for actual receipt tracking when those rows are not classified as internal transfers or pot movements (FR-M017). Attribution MUST be available at transaction level and via confirmed income patterns. Credits matching a confirmed income pattern MUST be auto-attributed as income unless the user has reassigned them. Attributed income credits MUST be distinct from expense categorisation and MUST NOT count as category spend actuals.
- **FR-M011**: The system MUST support only two allocation presets: 50/30/20 (default) and 75/15/10 (alternative), applied to the three fixed categories only. When the user changes preset on the standing plan, the system MUST immediately recalculate category allocation amounts from **estimated income** (cadence-normalised per FR-M031) using the new preset; recorded funding, report-scoped actual activity, and standing recurring expense inputs MUST remain unchanged until the user edits them.
- **FR-M012**: The system MUST NOT allow removal, replacement, or custom percentages for the three budget categories in v1.
- **FR-M013**: The system MUST support optional bank pots with no pot hierarchy or independent preset ratios. Each pot MUST map to exactly one of Needs, Wants, or Savings & Debt. The user MUST choose one of three **pot mapping modes**: **category-only** (**FR-M014**), **three pots**, or **several pots**. In **category-only** mode the system MUST NOT offer mapped-pot CRUD or enforce pot-count limits; expense and funding workflows operate at category level only. In **three pots** and **several pots** modes, mapping pots to categories is optional (a category MAY have zero mapped pots). In **three pots** mode the system MUST enforce at most **three** mapped pots in total and at most **one** mapped pot per category, with a strict one-to-one category↔pot link for every mapped pot. In **several pots** mode the system MUST allow multiple mapped pots per category while each pot still maps to only one category. When the user switches from **several pots** to **three pots**, the system MUST block the switch until surplus mappings are removed so three pots mode invariants hold. When the user switches to **category-only** from a pot mapping mode, the system MUST block the switch until all mapped pots are deleted per **FR-M013c**.
- **FR-M013b**: When the user assigns an expense **category** while optionally assigning a mapped pot (recurring confirmation, one-off categorisation, merge/split of expense patterns, and per-transaction expense reassignment) and the active mode is **three pots** or **several pots**, the system MUST apply default pot selection to reduce manual work: in **three pots** mode, when the selected category has a mapped pot, that pot MUST be pre-selected; when it has none, pot MUST default to none. In **several pots** mode, when **exactly one** pot maps to the selected category, that pot MUST be pre-selected; when zero or more than one pot maps to the category, the system MUST NOT pre-select a pot until the user chooses. In all cases the user MUST be able to set the pot to **none** or change to any other pot valid for the selected category. When the user changes category after a pot was pre-selected, defaults MUST be recomputed per the rules above. In **category-only** mode the system MUST NOT offer optional pot assignment on those flows.
- **FR-M013c**: The system MUST allow the user to **edit** and **delete** mapped bank pots. **Edit** MUST allow updating the pot display name (to match Monzo) and changing the mapped category, subject to **FR-M013** mode invariants. **Delete** MUST allow removing surplus pots when switching toward three pots mode, toward **category-only** mode, or when a pot no longer exists in the user’s bank setup. When a mapped pot is deleted, optional pot references on confirmed recurring expense items MUST clear to none; statement transactions MUST remain. When the pot has **non-zero** pot-level **recorded funding** (**FR-M015**), delete MUST prompt the user to **roll** that amount into the parent category’s recorded funding (counted once at category level) or **discard** it; non-zero funding MUST NOT be deleted without explicit confirmation that states the chosen outcome. Zero funding MAY delete without an extra funding prompt.
- **FR-M014**: The system MUST allow budgeting directly by category without bank pots via explicit **category-only** pot mapping mode (**FR-M013**). Category-only MUST be a first-class mode choice, not only “several or three pots with zero mapped pots”.
- **FR-M015**: The system MUST record amounts already set aside separately from planned future funding at category or mapped-pot level.
- **FR-M016**: Imported statements MUST NOT move money, set live bank-pot balances, or auto-establish funding without user recording.
- **FR-M017**: For the selected **report date range**, the system MUST show allocation, recorded funding, actual activity, and under/over per category, counting each amount once in category totals. Category **allocation** for the range MUST be the **FR-M031** monthly category allocation **prorated** to that inclusive report date range using **day-based proration**: monthly-equivalent allocation × (inclusive calendar-day count in the range ÷ **30.4375**), with money rounded at report boundaries per implement (**FR-M036**). The same divisor and formula MUST apply on category health, budget balance, and runway (**FR-M020**) so allocation, actual activity, and under/over refer to the same time window. **Under/over** MUST equal that range’s category allocation minus category actual activity for that range; recorded funding MUST be displayed separately and MUST NOT be included in the under/over calculation. Category **actual activity** MUST equal **net attributed spend** for that category in the range: the sum of expense debits attributed via match to a confirmed recurring expense pattern or via one-off transaction categorisation, minus attributed refunds or merchant credits under the same attribution rules. Unattributed debits MUST NOT be allocated across categories. Unattributed refunds or credits MUST NOT reduce category actual activity until assigned. Rows identifiable as **internal transfers or pot movements** (non-merchant spend) MUST NOT enter category actual activity or uncategorised spend unless the user explicitly one-off categorises them as spend.
- **FR-M017a**: When recorded funding or pot assignments cause mapped-pot plus unassigned amounts to exceed a category’s **report-scoped prorated allocation** (**FR-M017**), the system MUST persist the user’s entries and MUST display a persistent visible over-allocation indicator on category health until corrected.
- **FR-M017b**: For the selected report date range, the system MUST total imported expense debits that are not attributed to any category (per FR-M017) as **uncategorised spend**, display that total separately from the three category actual figures, and show a persistent visible warning on category health until each such debit is assigned. Internal transfers and pot movements excluded under FR-M017 MUST NOT be included in this total.
- **FR-M018**: The system MUST compute required income per category, overall requirement, shortfall, limiting category for ratio-related shortfall, and a qualified yes/no budget balance with monetary gap using **estimated income** and **expense commitments** both scoped to the same **report date range**. **Estimated income** for comparison MUST be the **FR-M031** monthly-equivalent figure **prorated** to that inclusive range with the **same day-based proration rule** as category allocations (**FR-M017**: inclusive day count ÷ **30.4375**). Standing plan displays MAY show monthly-equivalent estimated income; the budget balance conclusion MUST use the range-prorated amount. **Expense commitments** MUST be derived only from **confirmed recurring expense patterns**, each projected into that range in a cadence-aware way: **fixed** patterns use the user-confirmed amount per occurrence times **occurrence count** in range, where occurrences are counted from the pattern’s stored **payment anchor** (latest attributed or vendor-matched payment by default; user may override per **FR-M008c**) stepping forward and backward per cadence: **weekly** and **fortnightly** by fixed day intervals from the anchor; **monthly** by whole calendar months from the anchor with **last-day-of-month clamp** when the anchor day is invalid in a target month (same month arithmetic as **FR-M020**), counting each stepped date inclusively inside the range; **annual/rare** by yearly stepping from the anchor for confirmed fixed annual bills; **variable** patterns use the user-confirmed **monthly estimate** stored on the pattern (see **FR-M008c**) **prorated** into the inclusive range with the **same day-based rule** as **FR-M017** (monthly estimate × inclusive day count ÷ **30.4375**, rounded per **FR-M036**); calendar-month overlap apportionment MUST NOT be used. The stored estimate MUST NOT be replaced by a live rolling average that changes without user edit or explicit acceptance of a suggestion. **Required income per category** MUST equal that category’s total projected expense commitments for the range divided by the category’s preset percentage for the active preset (if the preset percentage is zero, required income for that category MUST be zero). **Overall required income** MUST equal the **maximum** of the three per-category required incomes. **Limiting category** MUST be the category with the highest per-category required income; when two or more tie, the system MUST choose **Needs**, then **Wants**, then **Savings & Debt**. **Shortfall** MUST equal max(0, overall required income − range-prorated estimated income). The qualified **yes/no** conclusion and monetary gap MUST compare range-prorated estimated income to **overall required income** using that rule. Income patterns, one-off debits, recorded funding, and unattributed imports MUST NOT be treated as commitments for this calculation. Attributed actual income MUST remain separate and MUST NOT substitute for estimated income in the yes/no conclusion.
- **FR-M019**: Estimated income, attributed actual income, and expense actual activity MUST remain separate from forecasts in all balance and health views. The system MUST display the user’s confirmed **estimated income and cadence** alongside an **actual income indication**: the **monthly mean** of attributed income credits over a user-chosen rolling window of at most **twelve months** (**N**), using only credits the user has attributed as income (FR-M010b). The window MUST span **N whole calendar months** inclusive: **end anchor** = shared report date range **inclusive end** on period-scoped reports (**FR-M031a**), or **today’s calendar date** on plan settings and other non-report plan views; **start** = first calendar day of the month **(N−1) calendar months** before the month containing the end anchor (month arithmetic MUST use last-day-of-month clamping when needed, consistent with **FR-M020**). The indication MUST equal the sum of attributed credits with transaction dates from start through end anchor inclusive, divided by **N**. The window length **N** MUST be stored on the **standing budget plan** (same persistence model as other plan preferences such as forecast horizon); when the user has never set it, the default MUST be **3 months**. The user MAY change **N** at any time; it MUST NOT exceed twelve months and MUST NOT reset each browser session. When attributed history is shorter than the chosen window, the system MUST label coverage explicitly.
- **FR-M020**: The system MUST warn when a category is projected to run short over a **runway window** with optional pot detail. The **runway window** MUST be the inclusive period from the shared report date range **start** through a **runway end date** derived from report range **end** plus **N** whole calendar months from the user’s forecast horizon (**FR-M035**), **clamping** to the last calendar day of the target month when the day-of-month is invalid (for example 31 January plus one month → last day of February). **Projected category spend** for the warning MUST be the cadence-aware projection of confirmed recurring **expense** commitments across that entire runway window (**fixed** amounts per occurrence; **variable** patterns prorate the same user-confirmed **monthly estimate** as **FR-M018** using the **FR-M017** day-based rule over the runway window). **Category actual activity** in the comparison MUST use only the shared **report date range** (not the months beyond report end). **Category allocation** in the comparison MUST be monthly-equivalent preset allocation **prorated** to the full runway window (same deterministic rule as **FR-M017**). A runway warning MUST be shown when projected category spend exceeds `(runway-prorated category allocation − report-range category actual activity + category recorded funding)`, where recorded funding includes mapped-pot funding rolled into the category once only; when it does not exceed that amount, the system MUST NOT show a runway warning for that category for that runway window.
- **FR-M021**: The system MUST present a complete confirmed recurring income and expense summary with cadence, fixed or variable amounts, assignments, and income splits, **And** MUST expose edit and delete actions for each confirmed item per **FR-M008c**.
- **FR-M022**: The system MUST export the user’s current plan and stored transaction data on demand; the user MUST choose at export time between (1) a versioned JSON bundle (single JSON file or ZIP of JSON parts) and (2) a ZIP of CSV files including stored transactions and separate plan/metadata CSV. On hosted instances, export MUST require reauthentication per Session 2026-11-04 (password confirmation preferred; passkey step-up not required for v1).
- **FR-M023**: The system MUST permanently delete all of a user’s financial data on confirmed request. On hosted instances, permanent deletion MUST require reauthentication per Session 2026-11-04 before erasure completes.
- **FR-M024**: The system MUST provide a local-only, account-free single-user mode that MUST NOT be exposed over a network.
- **FR-M025**: Every hosted instance MUST require user authentication and MUST isolate financial data per account (single-owner access: signed-in users see and change only their own plan and transactions). v1 hosted authentication MUST use ASP.NET Core Identity with email/password registration, sign-in, and sign-out; passwords MUST be stored hashed by Identity with no plaintext retention. Hosted v1 MUST NOT require passkeys for sign-in or data access. Optional passkeys (password primary, passkey optional on login/register/manage when implemented, aligned with the .NET Blazor Identity template pattern) are deferred beyond v1.0.0 acceptance unless explicitly added in a later milestone; hosted v1 MUST NOT offer passkey-only login or prohibit non-passkey login. When sign-in fails or account access is blocked, the system MUST guide users through standard Identity flows (register, sign-in, forgot password where implemented, lockout messaging).
- **FR-M026**: The system MUST operate in GBP for v1 monetary amounts; uploads containing non-GBP transactions MUST be rejected (whole file or affected rows) with a clear error and MUST NOT allow user override to import non-GBP amounts. The system MUST collect only minimal personal data necessary for function.
- **FR-M027**: Hosted deployments MUST encrypt financial data at rest and in transit; the system MUST NOT share financial data with third-party financial-data aggregators.
- **FR-M028**: The system MUST validate and sanitise all user inputs, including uploads and form fields.
- **FR-M029**: The system MUST NOT log raw statements, full account numbers, or secrets.
- **FR-M030**: The system MUST support safe self-hosting documentation outcomes (export, deletion, isolation) as user-facing capabilities, not implementation choices.
- **FR-M031**: v1 MUST provide exactly **one standing budget plan** per user (allocation preset, **estimated income** amount, **income cadence** of weekly, fortnightly, monthly, quarterly, or yearly, and confirmed recurring items; no library of multiple saved plan profiles). Plan settings MUST NOT require a budget start or end date. Until the user has **saved** both estimated income amount and income cadence, category **allocation** amounts and **FR-M018** budget balance outputs MUST display an explicit **not set** (or equivalent incomplete) state and MUST NOT treat planned income as **£0** for preset maths or yes/no conclusion. Primary reports (category health, budget balance) MUST remain accessible; the system SHOULD surface a non-blocking prompt to complete plan income. Optional estimated-income suggestions MUST NOT apply to stored allocations until the user explicitly confirms or edits per the paragraphs below. **Monthly-equivalent** income MUST be derived from the user’s stated amount and cadence using **pay-period factors**: weekly amount × 52÷12, fortnightly × 26÷12, monthly × 1, quarterly amount ÷ 3, yearly amount ÷ 12 (intermediate maths MAY use full precision; money rounds at report or display boundaries per **FR-M036**). **Monthly-equivalent** category allocation amounts MUST equal the chosen preset percentages applied to that monthly-equivalent income. Report-scoped views (**FR-M017**, **FR-M020**, and related indicators) MUST **prorate** those monthly category allocations to the selected report date range. The system MAY suggest estimated income and cadence from confirmed income patterns or attributed credits; it MUST NOT update stored estimated income or category allocations from such a suggestion until the user explicitly confirms or edits the figures (including after import or income-pattern changes).
- **FR-M031a**: Reports and period-scoped totals MUST use a user-selected **report date range** with inclusive start and end calendar days for transaction inclusion, category actual activity, expense commitment projection (FR-M018), and related report outputs. v1 MUST maintain **one shared report date range per browser tab** across all report views in that tab (category health, budget balance, runway warnings, and related outputs); updating the range on any one of those views MUST update the shared range for the other views in the **same tab** without requiring re-entry. Separate browser tabs MUST maintain **independent** in-tab ranges; updating range in one tab MUST NOT change another tab’s range. When the user opens a report view in a tab and no in-tab range is set yet, the system MUST default to the **current calendar month** (inclusive first day through inclusive last day of the month containing today). The report range MUST be independent of pay schedules and independent of income cadence. Changing the report range MUST NOT change the standing plan’s estimated income or confirmed recurring items. The range MUST remain non-persistent across visits (**FR-X006**); the system MUST NOT persist saved report-range presets on the standing plan in v1.
- **FR-M032**: The system MUST disclose statement-history gaps and uncertain income dates or amounts where they affect forecasts or warnings.
- **FR-M033**: The system MUST NOT imply that future costs are covered by money not yet received.
- **FR-M034**: For confirmed recurring variable expenses, the system MUST compute the last **three whole calendar months’** average monthly total (vendor-matched spend in each month) when available, or shorter available history with explicit coverage labelling, to **suggest** initial or updated **monthly estimates** at confirm, merge, split, or edit (**FR-M008c**). The suggestion window MUST end on **today’s calendar date** (inclusive) at the time of computation; it MUST NOT use the shared report date range end. Changing the report date range MUST NOT recompute or auto-apply suggestions. The stored monthly estimate used for **FR-M018** and **FR-M020** MUST remain stable until the user saves an edit or explicitly accepts a suggestion; imports and detection MUST NOT replace it automatically.
- **FR-M035**: Default forecast horizon MUST be **three months** with user override on the **standing budget plan**. **N** MUST be an integer **from 1 through 12 months** inclusive; the system MUST NOT persist values outside that range. The horizon MUST set the **runway window** inclusive end to report range **end** plus **N** whole calendar months with **last-day-of-month clamping** when needed (**FR-M020**); it MUST NOT change the shared report date range used for category health, budget balance, or **FR-M018**.
- **FR-M036**: For the same stored transactions, confirmed recurring items, shared in-session report date range, preset, estimated income, and user-recorded funding, report totals MUST be identical on repeat viewing across report pages (no non-deterministic drift for unchanged inputs). Golden budgeting tests (**SC-004**) MUST use the **30.4375**-day average month for all proration in expected results. **Money rounding:** all GBP amounts **emitted on reports** (and in golden expected results) MUST be rounded to **two decimal places** using **banker's rounding** (round half to even) at each report boundary; intermediate maths MAY retain full precision until that emission step.
- **FR-M037**: The system MUST support genuine one-off transaction categorisation at transaction level in v1.0.0. One-off categorisation MUST apply to expense debits, refunds, and merchant credits; it MUST affect category actual activity only (debits increase net spend, refunds/credits decrease it) and MUST NOT create forecast or guessed future recurring purchases. When one-off categorisation includes an optional mapped pot, pot default selection MUST follow **FR-M013b**.

### Key Entities *(include if feature involves data)*

- **User**: Person using Potsure; in hosted mode has an authenticated Identity account (email/password) with isolated data; in local-only mode operates without remote account.
- **Standing budget plan**: The single user-maintained plan profile: allocation preset, estimated income amount, income cadence, confirmed recurring items, forecast horizon (**FR-M035**), and attributed actual-income rolling window length (**FR-M019**, default three months). No plan start or end dates; changes apply to the same standing plan (no saved plan library).
- **Report date range**: User-selected inclusive start and end calendar days for report-scoped totals, category actual activity, and expense commitment projection; independent of pay schedule and income cadence. **One shared value per browser tab** across report views in that tab (**FR-M031a**); not synced across tabs; not persisted on the standing plan (**FR-X006**); defaults to **current calendar month** on first report open in a tab when unset (**FR-M031a**).
- **Budget category**: One of Needs, Wants, Savings & Debt; fixed for v1; receives allocation from preset percentages of cadence-normalised estimated income.
- **Allocation preset**: Either 50/30/20 (default) or 75/15/10 (alternative); applies only at category level.
- **Pot mapping mode**: One of **category-only** (no mapped pots; **FR-M014**), **three pots** (at most three mapped pots, at most one per category, one-to-one category↔pot), or **several pots** (unlimited pots, multiple per category allowed). Mode switches that would violate invariants are blocked until surplus pots are removed (**FR-M013**, **FR-M013c**).
- **Bank pot (optional)**: User-defined label mapped to exactly one category; no hierarchy; no own ratio; optional per category in both modes.
- **Statement upload**: Monzo CSV file with auto-detected or user-adjusted column mapping (confirmed before import), import status, errors, de-duplication outcome, and remembered mapping when layout unchanged.
- **Transaction**: Dated monetary movement from imports; basis for actual activity and detection input; may be classified as merchant spend, income, refund/credit, or internal transfer/pot movement when identifiable from statement data. Uniqueness for storage uses Monzo Transaction ID when imported, else date + amount + normalised description (per FR-M004 normalisation rules) for de-duplication.
- **Detected pattern**: Suggested recurring income or expense with cadence and amount behaviour; not active until confirmed; MUST NOT be generated from transactions classified as internal transfers or pot movements. **Rejected** suggestions remain unconfirmed; reject does not permanently block re-suggestion for the same grouping (**FR-M008**).
- **Confirmed recurring item**: User-approved pattern with assignments (category, optional pot, optional free-text tag for expenses; splits for income) and user-chosen **fixed or variable amount behaviour** per **FR-M008d** (may differ from the system’s initial inference). User MAY edit or delete per **FR-M008c**. Expense items contribute to **expense commitments** when projected into the selected report date range; income items support attribution (FR-M010b) but do not drive category allocations. Tags and income category splits are display-only labels and MUST NOT affect allocations, expense actuals, attributed actual income, commitments, or budget balance. Confirmed **income** patterns MUST have category splits totalling 100%.
- **Amount behaviour (fixed vs variable)**: Whether a confirmed recurring pattern treats amounts as stable (**fixed**) or history-driven (**variable**) for commitments and forecasts; user override always allowed at confirm, merge, split, and edit (**FR-M008d**).
- **Income allocation splits**: Per confirmed income pattern, percentages assigned to Needs, Wants, and Savings & Debt; MUST sum to 100% (validated on save); display-only - MUST NOT drive category allocations, actual receipt attribution, or FR-M018 maths.
- **Expense tag (optional)**: User-entered free-text label on a confirmed recurring expense; shown in the recurring summary and related lists; no effect on allocations, actuals, commitments, or budget balance.
- **Payment anchor (fixed recurring expense)**: Calendar date from which cadence-based occurrence counting steps for **FR-M018** and **FR-M020**; default = latest attributed matching debit, else latest vendor-matched debit; user MAY override at confirm/edit per **FR-M008c**; non-overridden anchor MAY advance when newer matching payments import. **Monthly** fixed patterns step whole calendar months from the anchor with last-day-of-month clamp; all cadences count stepped dates inclusively inside the projection range.
- **Expense commitment (budget balance)**: Cadence-aware projection of a confirmed recurring **expense** pattern’s expected cost into the selected report date range (or runway window for **FR-M020**); **fixed** patterns use amount per occurrence × occurrence count in range from the **payment anchor** (weekly/fortnightly interval stepping; **monthly** calendar-month stepping with clamp; **annual/rare** yearly stepping); **variable** patterns prorate the user-confirmed **monthly estimate** with the **FR-M017** day-based rule (÷ **30.4375**). Stored estimate stable until user edit or explicit suggestion acceptance. Sole input class for FR-M018 commitment totals (excluding income patterns, one-offs, funding, and imports).
- **Estimated income**: User-confirmed expected income amount and cadence (what they know today); distinct from attributed actual income. Until both are saved, allocations and **FR-M018** show **not set**, not zero-income maths (**FR-M031**). **Monthly equivalent** = pay-period factors per **FR-M031**; category allocations = preset × monthly equivalent once saved. **FR-M018** compares **range-prorated** monthly-equivalent estimated income to required income for the selected report date range (**FR-M017** proration rule). The system MAY suggest amount and cadence from confirmed income patterns or attributed credits but MUST apply allocations only after user confirmation or edit.
- **Attributed actual income**: Statement credits the user has attributed as income (FR-M010b); tracked separately from estimated income and from expense actuals. **Monthly mean indication** = sum of attributed credits in the **FR-M019** rolling window ÷ **N**; window ends on report range end (reports) or today (plan settings); length **N** stored on standing plan (default **3 months**, max twelve months).
- **Recorded funding**: Money user declares already set aside toward a category or mapped pot; distinct from planned future funding.
- **Planned future funding**: User-intended additional funding not yet recorded as set aside.
- **Assignment memory**: Stored user corrections and category/pot/tag choices applied on subsequent imports; includes per-transaction reassignments overriding auto-attribution from confirmed recurring matches.
- **Category health snapshot**: Allocation, recorded funding, actual activity, under/over for a report date range, optionally broken down by pot; **allocation** = monthly-equivalent category allocation from the standing plan **prorated** to that inclusive range (**FR-M017**); **actual activity** = net attributed spend (attributed debits minus attributed refunds/credits); **under/over** = range allocation − range actual activity (recorded funding excluded from under/over); excludes unattributed debits from category actuals (see uncategorised spend).
- **Uncategorised spend**: In-period imported expense debits not yet attributed to a category via confirmed recurring match or one-off categorisation; excludes internal transfers and pot movements unless one-off categorised as spend; shown as a separate total with persistent warning until resolved.
- **Required income report**: Per-category required income = category expense commitments ÷ preset fraction; **overall required** = max of the three; **limiting category** = argmax with tie **Needs → Wants → Savings & Debt**; shortfall vs range-prorated estimated income.
- **Budget balance conclusion**: Qualified yes/no whether **range-prorated** estimated income ≥ **overall required income** (max-of-ratios rule above); monetary gap = shortfall when estimated income is below overall required (same inclusive report date range on both sides).
- **Forecast horizon**: User-configurable **N** months (**1–12** inclusive, default **three**, persisted on standing plan) that extend the **runway window** beyond the shared report date range end (**FR-M020**, **FR-M035**); does not alter report range on other reports. **Runway end date** = report range end plus **N** calendar months with last-day-of-month clamp when the day is invalid. **Runway window** = inclusive report start through that runway end; compares projected commitments over that window to runway-prorated allocation minus report-range actual activity plus recorded funding.
- **Export bundle**: Portable copy of plan and stored transactions; user-selected format is either a versioned JSON bundle or a CSV ZIP (transactions plus plan/metadata CSV), each documented for portability.
- **Deletion request**: Irreversible removal of all user financial data.

## Assumptions

- Target currency for v1 is GBP; users primarily hold UK Monzo accounts with exportable CSV history.
- Users accept that recurring detection is probabilistic; the product communicates uncertainty rather than guaranteeing completeness.
- Self-hosted operators follow published secure deployment guidance; the product provides export and deletion but does not manage their infrastructure.
- “Lazy believer” remains the primary persona; frequent daily review uses the same plan and reports without a separate product mode.
- v1 planning uses one standing budget plan plus in-session report date ranges; saved plan libraries are out of scope (**FR-M031**, **FR-X006**).
- Estimated income and cadence may be suggested from confirmed income patterns or attributed credits; user confirmation or edit is required before allocations change (**FR-M031**).
- Household users think in standing bills and estimated pay cadence, not plan start/end dates; report date ranges are for viewing activity only (**Session 2026-11-09**).
- Users expect to revise confirmed recurring amounts when contractual costs change (rent, subscriptions); edit/delete on recurring items and pots is required for trustworthy low-touch upkeep (**G1**).
- Detection of fixed vs variable amounts is heuristic; users MUST be able to correct misclassification without fighting the system (**FR-M008d**).
- Monzo CSV column layouts remain stable enough for explicit mapping; breaking bank format changes are handled as import errors, not silent fixes.
- Hosted v1 baseline authentication is ASP.NET Core Identity email/password (register, sign-in, sign-out) with per-user data isolation; optional passkeys may follow the .NET Blazor Identity template pattern in a later milestone but are not required for v1.0.0 acceptance. Identity template **ForgotPassword** may be present; self-host v1 MAY use a no-op email sender (see [plan.md](./plan.md) Identity section). Broader account rescue flows (e.g. one-time keys generated at signup) remain deferred post-v1.
- One-off transaction categorisation is a v1.0.0 release requirement (FR-M037); forecasts MUST NOT treat one-offs as recurring commitments.
- Trend reporting (Could) is omitted from v1 release success unless explicitly pulled into scope later.
- No third-party open banking or aggregation is assumed; statements are user-uploaded files only.
- Legal and regulatory compliance beyond stated privacy minimisation and user-controlled deletion is the operator’s responsibility; the product provides the technical means for portability and erasure.
